# Ticket 4: star schema DDL -> Delta (gold)

Source: `sql_scripts/01_create_tables.sql` (SQL Server `DWH`). Target: Delta tables in Unity Catalog,
created from `sql/gold/*.sql` by `banking_etl.gold.ddl.apply_star_schema` (notebook
`notebooks/gold/create_star_schema.py`, bundle job `gold_create_star_schema` in
`resources/ticket-04-delta-ddl.yml`).

| SQL Server | Delta | Notes |
|---|---|---|
| `DWH.dbo.DimBranch` | `gold.dim_branch` | + `BranchKey` identity |
| `DWH.dbo.DimAccount` | `gold.dim_account` | + `AccountKey` identity |
| `DWH.dbo.DimCustomer` | `gold.dim_customer` | + `CustomerKey` identity |
| `DWH.dbo.FactTransaction` | `gold.fact_transaction` | + `AccountKey`, `BranchKey` (dim lookups) |
| FK violations / Talend reject flow | `ops.fact_transaction_rejects` | fact columns + `reject_reason`, `rejected_at` |

## Type mapping

| SQL Server | Delta | Columns |
|---|---|---|
| `INT` | `INT` | all `*ID`, `Age` |
| `MONEY` | `DECIMAL(19,4)` | `Balance`, `Amount` (same precision/scale as MONEY; no float rounding) |
| `DATETIME` | `TIMESTAMP` | `TransactionDate` (session time zone UTC; values are wall-clock, no offset) |
| `DATE` | `DATE` | `DateOpened` |
| `VARCHAR(n)` | `STRING` | lengths are not enforced; the original length is kept in the column comment |
| (new) | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `BranchKey`, `AccountKey`, `CustomerKey` |

Column names keep the legacy PascalCase for reconciliation parity. Every table and column has a
comment. Talend's output schemas used narrower types (`Balance`/`Amount` as `INT`, `DimCustomer.Age`
as `VARCHAR(3)`), but they wrote into the tables created by `01_create_tables.sql`
(`TABLE_ACTION=CREATE_IF_NOT_EXISTS`), so the DDL script is the source of truth.

## Constraints: what Delta enforces vs what is informational

| Constraint | Where | Enforced? |
|---|---|---|
| `NOT NULL` on natural keys (`BranchID`, `AccountID`, `CustomerID`, `TransactionID`) | dims, fact | **Yes**, by Delta on every write |
| `NOT NULL` on `reject_reason`, `rejected_at` | rejects | **Yes** |
| `CHECK (Age IS NULL OR Age BETWEEN 0 AND 150)` (`ck_dim_customer_age`) | dim_customer | **Yes**, by Delta on every write |
| `PRIMARY KEY` (`pk_dim_branch`, `pk_dim_account`, `pk_dim_customer`, `pk_fact_transaction`) | UC only | **No** (informational; `information_schema.table_constraints.enforced = 'NO'`) |
| `FOREIGN KEY` (`fk_fact_transaction_dim_account`, `fk_fact_transaction_dim_branch`) on the natural keys | UC only | **No** (informational) |

How uniqueness and referential integrity are guaranteed in code instead:
- **Dim uniqueness**: dims are written only through `banking_etl.gold.merge.merge_scd1`, which MERGEs on
  the natural key and raises if the source has duplicate or NULL keys, so the PK is never violated.
- **Fact uniqueness**: ticket 8 dedupes `silver.transaction` on `transaction_id` (Talend `tUniqRow`).
- **Fact -> dim FKs**: ticket 8 left-joins the fact to `dim_account` / `dim_branch` on the natural keys to
  get `AccountKey` / `BranchKey`; rows with no match go to `ops.fact_transaction_rejects`
  (`reject_reason` e.g. `MISSING_DIM_ACCOUNT`, `MISSING_DIM_BRANCH`) instead of `gold.fact_transaction`.
  This replaces the SQL Server FK error, which Talend (`DIE_ON_ERROR=false`) sent to its reject flow.
  Ticket 10's reconciliation/DQ can assert `fact_transaction` has no NULL `AccountKey`/`BranchKey`.
- `AccountID`/`BranchID`/`AccountKey`/`BranchKey` stay nullable on the fact (as in SQL Server, where a
  NULL FK passes); ticket 8 decides whether NULL ids are rejected (README: unmatched -> rejects).
- No `RELY` on the PKs: the optimizer must not assume uniqueness it cannot verify.
- `DimAccount.CustomerID` has no FK in the legacy DDL, so none is added.

## Delta table properties

- Dims: `delta.enableChangeDataFeed = true` (downstream can read SCD-1 changes), plus
  `delta.autoOptimize.optimizeWrite` / `autoCompact = true`.
- Fact and rejects: `optimizeWrite` / `autoCompact` only (full refresh; CDF would just record
  whole-table rewrites).

## Running locally vs on Databricks

`apply_star_schema(spark, settings, unity_catalog=None)` defaults `unity_catalog` to
`settings.catalog is not None`.
- `unity_catalog=True`: SQL runs as written (`/*uc:begin*/.../*uc:end*/` markers removed, PK/FK kept).
- `unity_catalog=False` (local OSS Delta): PK/FK blocks are stripped. OSS Spark 4.0 + Delta 4.0 reject
  `GENERATED ... AS IDENTITY` in SQL DDL, so `CREATE TABLE` statements with identity columns are run
  through `DeltaTableBuilder` instead (same columns, comments, nullability, identity, comment, properties).
- DDL is `CREATE TABLE IF NOT EXISTS` + drop/add of CHECK constraints, so re-runs are no-ops for existing
  tables (schema changes need an explicit `ALTER TABLE`).
- `ensure_schemas=True` runs `CREATE SCHEMA IF NOT EXISTS` for gold/ops (ticket 1 owns the full setup).

## SCD-1 helper (`banking_etl.gold.merge.merge_scd1`)

`merge_scd1(spark, source_df, target_table, key_cols, update_cols=None) -> dict` for tickets 5/6/7:
- MERGE on `key_cols`; matched rows are updated only if some `update_cols` value differs (`<=>`,
  null-safe), so re-running the same source writes no rows; new keys are inserted; nothing is deleted.
- Only `key_cols + update_cols` are written; identity columns are rejected, so surrogate keys are
  generated once and never change. `update_cols` defaults to all non-key source columns.
- Source columns are cast to target types (e.g. DOUBLE -> DECIMAL(19,4)); extra source columns are
  ignored when `update_cols` is given.
- Raises `ValueError` for duplicate/NULL keys, missing columns, key/update overlap or identity columns.
- Returns `numSourceRows`, `numTargetRowsInserted`, `numTargetRowsUpdated`, `numTargetRowsDeleted`
  from the Delta MERGE metrics.
