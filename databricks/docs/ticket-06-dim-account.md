# Ticket 6: Talend `Load_DimAccount` -> silver / gold

Source job: `talend_jobs/Load_DimAccount.zip` (`process/Load_DimAccount_0.1.item`).

```
tMSSqlInput (tDBInput_1)  ->  tMap_1  ->  tMSSqlOutput (tDBOutput_1)
sample.dbo.account            1:1         DWH.DimAccount (context.namaTabelTujuan = "DimAccount")
```

| Talend | Setting | Databricks |
|---|---|---|
| `tDBInput_1` query | `SELECT account_id, customer_id, account_type, balance, date_opened, status FROM dbo.account`, `TRIM_ALL_COLUMN=false` | `bronze.sqlserver_account` (ticket 2) |
| `tMap_1` | no Var table, no filter, no lookup; every output column is `row1.<col>`; `DIE_ON_ERROR=true` | `banking_etl.dims.account.transform_silver_account` + `to_dim_account` |
| `tDBOutput_1` | `TABLE_ACTION=CREATE_IF_NOT_EXISTS`, `DATA_ACTION=INSERT`, `DIE_ON_ERROR=false` (reject flow not connected) | `ensure_dim_account` + `merge_scd1` on `AccountID` |

## Column mapping

| Source (`dbo.account`) | silver.account | gold.dim_account | Conversion |
|---|---|---|---|
| `account_id int NOT NULL` | `account_id INT` | `AccountID INT NOT NULL` | none; NULL or duplicate fails the load |
| `customer_id int` | `customer_id INT` | `CustomerID INT` | none |
| `account_type varchar` | `account_type STRING` | `AccountType STRING` | none (no trim / case change) |
| `balance int` | `balance DECIMAL(19,4)` | `Balance DECIMAL(19,4)` | int -> MONEY (exact) |
| `date_opened datetime2` | `date_opened DATE` | `DateOpened DATE` | datetime2 -> DATE (time of day dropped, as SQL Server does on insert) |
| `status varchar` | `status STRING` | `Status STRING` | none: values stay `active` / `terminated` (`sp_BalancePerCustomer` filters `Status = 'active'`) |
| - | `_ingested_at`, `_source` | - | lineage carried from bronze |
| - | - | `AccountKey BIGINT IDENTITY` | generated by Delta, never written by the load |

The Talend output schema types `Balance` as `Integer` and `DateOpened` as `Date` with a
`dd-MM-yyyy` display pattern; the actual stored types come from `01_create_tables.sql`
(`MONEY`, `DATE`), which is where SQL Server converts the values. Silver applies those conversions,
so gold is a pure rename.

## Load semantics and deviations

- **NULL `account_id`**: non-nullable in the Talend schema, so the generated code throws
  "Null value in non-Nullable column" and the job dies. `transform_silver_account` raises `ValueError`.
- **Duplicate `account_id`**: Talend inserts the first row and the PK violation sends the rest to the
  (unconnected) reject flow. The source has a PK on `account_id` so this cannot happen; the port
  raises instead of picking an arbitrary row.
- **Re-runs**: Talend `INSERT` into an existing `DimAccount` rejects every existing key (PK
  violation, `DIE_ON_ERROR=false`), so changed attributes are never updated. Per the migration
  conventions the port is **SCD-1** (`merge_scd1`): changed rows are updated in place, new rows
  inserted, nothing deleted, `AccountKey` stable. Initial loads are identical either way.
- **silver.account** is a full overwrite of the latest bronze snapshot (`overwriteSchema=true`).

## Parity evidence

`fixtures/parity/dwh_dim_account.csv` is `DWH.DimAccount` produced on SQL Server 2022 (Docker,
`data_sources/sample.bak` restored, `sql_scripts/01_create_tables.sql` applied) by the same
statement the Talend job issues per row:
`INSERT INTO DimAccount (AccountID, CustomerID, AccountType, Balance, DateOpened, Status) SELECT ... FROM sample.dbo.account`.
`tests/dims/test_account.py::test_gold_initial_load_parity_with_talend_dwh` asserts the gold
table equals it exactly (21 rows, SUM(Balance) = 624,000,000.0000, 18 `active` / 3 `terminated`).
